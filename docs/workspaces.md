# 临时工作区管理

配置中的 `local.release_root`（通常叫 `releases`）是本机临时处理目录，与 GitHub Releases 下载页分开。预处理需要保存标准副本、转码结果和报告，所以单独点击“预处理曲目”也会创建一个批次；只做“检查资源”或打开工作区列表不会创建批次。

一个工作区代表一批**暂存但尚未提交**的改动，保存新增文件、占位谱面、累计总表、定数草稿、待核验的购买候选、各阶段进度与服务器配置。02 上传后仍保留完整内容；只有完成 03 并确认提交后才销毁。提交表示整批流程验收完成，不能撤销已经安装、上传或执行的 API 操作。

## 查看、继续与删除

启动时若存在未提交工作区，会提示继续上次工作或打开列表。选择新目录时，也会提示追加到当前工作区、继续已有工作区，或明确另建独立工作区；取消不会更换目录。“新建批次…”保留旧内容，适合分别处理不同 server。

“工作区管理…”汇总该配置档此前登记的发布目录，展示各批次状态、曲目数、ERROR 与服务端。继续时恢复该工作区保存的路径、version、应用版本、SSH / API 设置和执行进度；API Token 仍从所记环境变量名读取，私钥只保存文件路径，不复制凭据内容。旧工作区缺少完整快照时会使用现有配置补齐，需要核对对应服务器。

尚未进入 01 的纯预处理批次继续时，会重新扫描并比较输入与副本哈希：

- 未改变且校验通过的成功曲目直接复用，避免重复复制和转码。
- 失败、发生变化或新增的曲目重新处理，先前的 ERROR 会按当前输入重新判断。
- 已删除、变为无效或不能复用的旧副本移出 `songs/`，保留在 `work/previous-*`，并报告 WARNING，避免遗留资源混入本次更新或丢掉人工编辑。
- 旧版报告没有输出哈希时，可在同一目录继续，但首次会保留旧副本并重新生成，不将缺少证据的副本直接当成成功。

处理完每首曲目都会保存报告检查点。正常处理结束时 `complete=true`；有 ERROR 时仍然 `valid=false`。进程中断会留下未完成批次，操作系统自动释放进程锁，下次可继续。报告损坏但仍有有效归属标记的批次可手动清理；无法识别归属的目录不能从程序删除。

查看历史报告只展示该次结果；点击“继续所选批次”才恢复工作流程。仅载入报告不会宣告资源已经恢复、构建或发布。已完成 01 的批次继续后，可以换目录再执行 01，累积准备结果。若追加失败，继续操作恢复待追加目录并重试，不把失败内容静默排除。

“放弃工作区…”需要单独确认，仅删除所选批次的暂存内容与进度，不会撤销已经发生的本地 / VPS 资源更新或 API 操作。原始包与其他工作区保留，同时失效窗口内该批次的引用。

## 同一批次累积准备

- 未开始 02 构建时，再次点击 01 默认追加到当前批次，可反复选择不同来源目录，也可重扫原目录。
- 追加前保存并关闭总表编辑器；程序读取磁盘上已保存的内容，无法读取记事本内尚未保存的草稿。完成后打开同一路径的总表，直到所有内容齐备再执行 02。
- 保留此前曲目、实际谱面、音频、曲绘、背景，以及已保存的 songlist、packlist 和 unlocks。新曲目从当前最大 idx 继续分配；重复 ID 追加难度，不重复添加整条记录。冲突保留审核值并报告 WARNING，真实资源冲突为 ERROR。
- 同一个待发布批次固定 version、本地目录基线和应用版本选项。需要另一个 version 或独立更新时，点击“新建批次…”，旧批次保留于列表。
- 成功轮次保留审核文档与记录快照，清理候选资源的重复大文件。失败轮次保留诊断与候选文件，修复后再次 01；02 上传后继续保留整个工作区，等待 03 与最终提交。
- 提交候选资源时使用恢复记录。进程中断后，通过“继续所选批次”恢复；不会用半份追加结果发布。02 会核验各来源与累计标准副本。

人工审核字段优先于再次导入的原曲目包，包含更改值、嵌套字段以及主动删除的字段；保护记录保存在 `publish.json`，后续多轮 01 也不会把这些字段补回。新增曲目和未审核过的新难度仍可合并；02 会对最终审核内容执行必要的格式与资源校验。旧版没有 `workspace.json` 的批次，可依据有效的 `report.json` 恢复；继续保存时补建标记，不重置审核总表。

工作区列表在后台读取，窗口先显示加载状态。首次 01 需要复制完整 active 并核验内容，耗时主要取决于 active 的大小与磁盘速度，而不只是本次曲目数量；日志显示各阶段及耗时。追加 01 在同一个工作区事务内复用未变化的文件，所有修改通过替换文件生成独立副本，审核文档独立复制；文件系统不支持时退回普通复制。原始曲目与生产 active 不参与文件复用。只读资源可正常进入工作区并完成清理。

## 03 验收后的提交与清理

03 成功后并不自动清理。用户点击“提交并清理…”，确认验收后，程序检查：

1. 本地资源安装、校验成功。
2. 本批 bundle、下载资源已上传，且远端内容校验成功。
3. 当前定数、购买候选所对应的曲目、操作选项和 API 目标已执行成功；全部 API 选项关闭时，已明确执行并记录跳过。
4. 完成后没有再次修改定数、选项或审核总表，资源文件与已发布清单保持一致。

任何错误或结果不明都保留工作区。上传失败继续同一 bundle；03 失败继续检查点，不会重新打包。修改已完成任务的定数或选项后，需重新执行 03，再确认提交。只关闭窗口、完成 02、收到单个 API 的成功响应，都不会自动销毁工作区。

清理后删除整个临时批次的大文件，在 `.history/<批次>.json` 留下很小的完成记录，不保存 Token 或其他凭据。若清理中途失败，记录 `cleanup_complete=false`，已发布资源不回退，可之后重试清理。`.locks/` 保存进程锁文件，不是曲目资源。

提交后的摘要记录 bundle 版本、审核哈希、03 完成指纹与所选操作；完成任务归档可保留最终定数与购买记录。不保存 Token 或私钥内容。

## 目录结构与命令行

```text
releases/
  preprocessed-<唯一后缀>/
    workspace.json       # 归属、输入与对应 server 的配置快照
    report.json          # 逐曲检查点、源文件与输出哈希
    songs/<id>/          # 当前成功标准副本
    work/                # 失败过程及不能复用的旧副本
    plan.json            # 合并草案及诊断
    publish.json         # 01/02 状态、哈希和固定构建清单
    server-task.json     # 本工作区的定数、购买候选与 03 进度
    receipt.json         # 02 核验凭据
    prepared/active/     # 完整 active 审核副本，songlist 可人工编辑
    prepared/database/   # 本批增量合并后的完整下载曲目
    bundle/              # 本批 .cb / .json
    backups/             # 本地就位覆盖前的文件备份，完成清理时删除
    additions/import-*/  # 追加候选、失败诊断和 before/ 审核快照
    append-transaction.json # 仅提交过程中存在的恢复记录
  .locks/                # 跨进程互斥
  .history/              # 发布完成后的简要记录
  .server-tasks/         # 已提交任务归档，以及独立手动上传任务
```

可选命令行继续仅预处理的批次，仍使用当前配置中的输入与 version，并检查原始输入目录是否匹配；已进入 01 的累计批次请从桌面继续：

```powershell
python -m arcaea_uploader preprocess --config config.local.json --resume releases/preprocessed-abcdefgh
```

`--resume` 与 `--scan-only` 不能合用。只读扫描仍不写工作区。

GUI 在其启动配置旁保存 `<配置文件名>.workspaces.json`，仅记已登记的发布目录和上次活动工作区，供重启发现多个 server 的未完成任务。它不含凭据；读取列表不创建发布目录。切换工作区只恢复窗口设置，不自动覆盖全局配置文件。
