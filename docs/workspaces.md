# 临时工作区管理

配置中的 `local.release_root`（通常叫 `releases`）是本机临时处理目录，与 GitHub Releases 下载页分开。预处理需要保存标准副本、转码结果和报告，所以单独点击“预处理曲目”也会创建一个批次；只做“检查资源”或打开工作区列表不会创建批次。

## 查看、继续与删除

更新页底部的“工作区管理…”列出当前工作区内的批次，可查看报告、继续预处理、打开目录或手动删除。新建批次始终使用独立名称；选择“继续预处理”才会复用选定批次，重启 Uploader 后仍可使用。

继续时恢复该批次的原始输入路径和 version，其余设置采用当前配置，允许先修正 FFmpeg 或资源路径。程序重新扫描原始包，比较配置、元数据、源文件及输出副本哈希：

- 未改变且校验通过的成功曲目直接复用，避免重复复制和转码。
- 失败、发生变化或新增的曲目重新处理，先前的 ERROR 会按当前输入重新判断。
- 已删除、变为无效或不能复用的旧副本移出 `songs/`，保留在 `work/previous-*`，并报告 WARNING，避免遗留资源混入本次更新或丢掉人工编辑。
- 旧版报告没有输出哈希时，可在同一目录继续，但首次会保留旧副本并重新生成，不将缺少证据的副本直接当成成功。

处理完每首曲目都会保存报告检查点。正常处理结束时 `complete=true`；有 ERROR 时仍然 `valid=false`。进程中断会留下未完成批次，操作系统自动释放进程锁，下次可继续。报告损坏但仍有有效归属标记的批次可手动清理；无法识别归属的目录不能从程序删除。

查看历史报告只展示该次结果；点击“继续预处理”完成重新核验后，标准副本才作为本次资源检查的输入。仅载入报告不会宣告资源已经恢复、构建或发布。

手动删除需要在窗口中确认。删除范围限定为所选的单个批次，清掉其工作副本、失败过程和报告；原始收集目录、active、本地 database 和其他批次保留。删除当前使用的批次后，同时失效窗口中的副本引用和检查报告，避免继续使用已删除的路径。

## 发布成功后的自动清理

完整 02 发布执行器**尚未接入**。已提供 `cleanup_published_workspace` 接口，未来由发布执行器在以下事实核验完成后调用：

1. 本地资源安装、校验成功。
2. 本批 bundle、下载资源已上传，且远端内容校验成功。
3. 已保存绑定最终 songlist 哈希、真实谱面清单及上传凭据的独立 03 小任务；或者明确跳过 03。

该接口要求批次 ID 和完整确认结果，预处理成功、SCP 退出码为 0 或关闭窗口均不触发清理。上传失败或文件状态不明时保留大文件，重试复用 bundle。03 已移出 02，上传完成后的 API 失败只保留独立小任务，详见[03 服务端操作](server-operations.md)。

清理后删除整个临时批次的大文件，在 `.history/<批次>.json` 留下很小的完成记录，不保存 Token 或其他凭据。若清理中途失败，记录 `cleanup_complete=false`，已发布资源不回退，可之后重试清理。`.locks/` 保存进程锁文件，不是曲目资源。

自动清理不影响本地 database 和 VPS 的双份最终资源。当前预览版不会伪造上传成功条件，也不会自动清理未发布批次；可通过管理窗口手动处理现有临时目录。

## 目录结构与命令行

```text
releases/
  preprocessed-<唯一后缀>/
    workspace.json       # 归属与原始输入记录
    report.json          # 逐曲检查点、源文件与输出哈希
    songs/<id>/          # 当前成功标准副本
    work/                # 失败过程及不能复用的旧副本
  .locks/                # 跨进程互斥
  .history/              # 发布完成后的简要记录
  .server-tasks/         # 不随批次删除的 03 定数、审核快照和 API 进度
```

可选命令行继续同一批次，仍使用当前配置中的输入与 version，并检查原始输入目录是否匹配：

```powershell
python -m arcaea_uploader preprocess --config config.local.json --resume releases/preprocessed-abcdefgh
```

`--resume` 与 `--scan-only` 不能合用。只读扫描仍不写工作区。
