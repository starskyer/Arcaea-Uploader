# 03 服务端操作与最终提交

03 从 02 的文件上传阶段独立出来。流程为 **01 准备审核 → 保存总表 → 02 打包上传 → 03 操作 → 确认提交**。API 操作可按选项跳过，工作区要到最终确认提交后才销毁。

01 已在工作区内保存定数草稿和本批购买候选。02 上传核验后交接到同一工作区的 `server-task.json`，保留所有资源和进度；也支持已手动上传的独立任务。预处理、检查和定数录入不会自行修改 VPS。

## 提交归档与后续修改

“提交并清理…”成功后，界面显示原任务的只读归档：可查看定数、购买候选和导出清单，不能编辑、保存覆盖或再次执行。重启后从“载入任务…”打开归档也保持只读；旧版归档根据 `.history` 的提交记录识别，不改写原文件。若旧版曾在提交后修改归档，界面会提示并保留现有内容。

点击“创建后续任务…”会在 `.server-tasks` 下生成独立 ID 的草稿，记录来源归档路径、哈希与原批次 ID。沿用归档内的曲目、实际难度、定数、购买安排及原上传确认，不依赖已清理的资源副本，也不更换资源总表。保持原 API 目标和操作选择，默认关闭资源刷新；其他选项仍可调整。

后续任务可修改定数与购买安排，再明确确认执行。未改变的已完成步骤复用，修改过的定数重新同步并刷新评分；已有购买项保留原价格和物品关联，新增 ID 才补缺创建。写入响应丢失时保留新任务进度，再查询远端继续，原提交归档和摘要始终保留。执行成功或明确全部跳过后，新任务自动归档只读；再次修改需再创建下一份后续任务，不再提示等待工作区提交。

## 界面与定数录入

1. 预处理或检查本批曲目，下方“03 · 定数与服务端”显示这批 SID、English name 和难度 0–4。
2. 双击实际谱面的定数单元格，输入后按 Enter 或点击“保存定数”。只保存用户填写的数据，不从 rating 推断。可填正数、`0.0` 或 `-1`，精度为整数或一位小数；`0.0` / `-1` 表示实际存在但不计评分的谱面，留空表示本次不指定。普通整数按 `.0` 显示，`-1` 保持显示为 `-1`。
3. 点击“审核总表…”选择人工保存、且确实用于本次上传的最终 songlist。03 只提取本批 ID，重新读取最终 `set`、`purchase` 和曲名，不继续使用原始单曲包中未审核的字段。`title_localized.en` 优先，缺少时取 `title`。
4. “选项…”可逐项跳过操作。“执行 03…”确认目标 API、上传情况及未填定数；全部关闭时明确记录跳过，不连接 API。成功后验收结果，点击“提交并清理…”完成整批工作区。

真实谱面难度以本次资源检查中的输入与本地服务端实际 AFF 并集为准，排除 timing-only 占位谱；不会把已存在的真实旧难度误记为空。没有实际谱面的单元格固定 `-1`，不能编辑。

## 上传前的购买项预览

03 页的“购买项预览”在 01 后即可使用，无需 API Token 或服务器连接，也不要求先完成 02。它把数据库 `purchase` 的价格与折扣信息、`item` 的物品类别和可用状态、`purchase_item` 的数量和关联关系合并为一条易读的候选：购买项、单曲/曲包、价格、原价、关联物品、引用曲目及状态。选中条目可查看数量 1、物品可用、无折扣、不允许兑换券等细节。

预览与实际执行共用推断规则：单曲 100、曲包 500；多首引用同一曲包时合并，免费曲目单独显示。无法推断的条目逐曲列为“确认后跳过”，其余有效候选仍可查看。字符串 `"null"` 不会自动当作免费或改写；可以保留原值，在执行 03 前确认跳过该购买项。

打开购买项页或点击“重新分析总表”会读取磁盘上最新保存的审核表，保留已录入定数；可“导出清单…”为 JSON。只分析和导出不调用 API，不创建购买项。状态“待远端核对”表示尚不能断定必然新增；03 实际执行时查询远端，已有项保持原价格、物品关联和赠品。实际 API 写入仍需先完成 02 上传核验。

双击条目或点击“编辑所选…”可选择自动推导、自定义、跳过购买项。自定义可修改购买项 ID、单曲/曲包类型和价格；无折扣，原价与价格相同。修改合并后的曲包项会应用到它的全部引用曲目。编辑仅保存本批 `server-task.json`，不改 songlist；自定义 ID 需与客户端引用核对。重新分析、再次 01、02 上传交接和重启恢复均保留这些安排，选择“自动推导”可恢复默认规则。服务器已经存在的购买项仍保持原配置。

点击“执行 03…”后，确认框会列出所有无法推断及人工选择跳过的条目。取消时不发送 API 请求；确认后仅跳过这些购买项并记录 WARNING，继续合法购买项、歌曲定数和所选刷新操作。确认绑定当前总表及购买安排；后续修改会使旧确认失效，必须重新确认。输入资源 ERROR、未完成 02 或实际 API 失败仍按原规则处理。

存在未填真实难度时弹窗，用户可返回补填，也可继续：**保留远端已有定数；新建记录的未填项暂用 -1**。空难度统一 `-1`。已有歌曲使用局部 PUT，未填写的真实难度不会覆盖已有值。SID 与曲名取自审核总表，增量添加难度也可以补录。

手填 `0.0` / `-1` 属于明确指定，不会触发“未填定数”确认，并会覆盖该难度原有的正定数；留空则保留已有值。无实际谱面的难度仍固定为 `-1`，不可编辑。

界面与 API 使用真实定数单位，服务器数据库的 `rating_*` 字段使用十倍整数：`9.7 → 97`、`0.0 → 0`、`-1 → -10`。历史 SQL 直接填写的数据库 `-1` 经 API 表示为 `-0.1`；这与 API 的 `-1` 是不同的数值表示，但服务端将所有非正定数视为 Unrank，均不产生正的定数评分。Unrank 仍保存分数和 best_score，并不会删除个人最佳记录；新成绩不会进入 recent30。修改已有定数后可执行 03 的“刷新评分”更新旧成绩对应的 rating。

旧服务端 `Chart.chart_const` 若使用 `if self.defnum` 判断未知值，会把数据库 `0` 回显为 API `-1`，无法精确核验手填的 `0.0`。应改为 `if self.defnum is not None`，使零值正常返回。Uploader 遇到这种回显会保留失败进度并说明原因；修复服务端后继续同一任务即可，已有零值正确匹配时不会重复写入。

## 执行顺序

| 顺序 | 操作 | 实际入口 |
| --- | --- | --- |
| 1 | 刷新 bundle、songs、world map | `refresh_content_bundle_cache` → `refresh_song_file_cache` → `refresh_world_map_cache` |
| 2 | 补充缺少的购买项 | `/items` → `/purchases` → `/purchases/<name>/items` |
| 3 | 新增 / 补充歌曲定数 | `POST /songs` 或 `PUT /songs/<sid>` |
| 4 | 刷新曲目定数对应的成绩评分 | `refresh_all_score_rating` |

第 4 项对应旧 Web 页 `/updatedatabase/refreshsongrating`，会重新计算 best_score、recent30 中已有成绩的评分；没有额外调用“刷新用户 PTT”操作。各项开始前先做只读鉴权和结构检查，所有写操作仍严格按上表顺序。

## 购买项规则

- 空 purchase 不创建购买项；`purchase == id` 为 `single`、价格 100；`purchase == set` 为 `pack`、价格 500。
- 同一个曲包被多首歌引用，只处理一次。purchase 不匹配两者、两者同时匹配或同名出现不同类别时不自动猜测；在预览中列出，允许编辑本批安排或经弹窗确认跳过，并以 WARNING 记录。
- 先查询远端。已存在的购买项保留价格、折扣和物品配置，不修改已有业务数据。
- 新建时 `price == orig_price`，折扣起止使用 2000 年的过去时间，`discount_reason` 为空，不启用兑换券购买。
- 新物品设为可用；已有但不可用的物品需要人工确认。先创建物品，再创建购买信息，最后关联一个同 ID 的 `single` / `pack`、数量 1。

API 请求后读回核验。若本任务创建购买项后中断，会记住创建意图，下次先读取服务端状态，再补未完成关联；不会因为“购买项已经存在”就误跳过半成品，也不会重设其他既有购买项。

## 保存、清理与重试

01 之后的任务和草稿位于工作区内，纯预检保持只读：

```text
<release_root>/<batch-id>/server-task.json
```

记录本批曲目、真实难度、人工定数、购买候选、审核哈希、选项与进度；资源文件同处工作区，不保存 Token 或密钥内容。购买候选依据最终 set / purchase 生成，03 查询远端后只补缺少项。通过工作区管理恢复可同时还原 server 配置。

02 使用 `confirm_uploaded(task, receipt)` 绑定上传凭据与最终总表；此时不清理。03 完成后记录当前曲目、定数、选项、上传确认及 API 目标的完成指纹；修改输入后不能凭旧完成状态提交。最后确认提交才清理临时资源，在 `.history` 留摘要、`.server-tasks` 留完成任务归档。独立手动上传任务也使用 `.server-tasks`，由用户确认上传情况。

每个 API 步骤保存检查点。任何失败停止后续步骤，不回退已成功的数据；后续使用同一任务继续。写请求不自动重试，超时或响应丢失可能意味着服务端已处理：购买项与歌曲先查询再补缺，刷新请求结果不明时需确认服务端处理结束再继续。安全 GET 遇到连接错误或 502/503/504 时最多再试一次；鉴权、证书验证与业务数据错误不重试。任务有跨进程锁和修订号，避免两个窗口同时执行或旧窗口覆盖新进度。若确认后的审核表又改变，必须重新载入并确认上传情况。

定数只预读本轮尚未完成的曲目，复用该次读到的记录；完成且输入未变的曲目不再逐首 GET。数据已经匹配时不重复写入。POST/PUT 返回完整且匹配的 song_id、曲名与五档定数时，用响应核验；旧接口返回不完整或不匹配时仍回查服务器，核验不一致会停止。下一次继续时重新查询未完成曲目，以确认上次写入状态。

### 系统代理与直连

配置页的“API 使用系统代理”默认勾选，兼容已有行为；Windows 上也会读取系统注册表中的代理，即使没有 HTTP_PROXY 环境变量。取消勾选后只有本工具管理 API 走直连，整机代理与 SSH 设置保持不变。对应 JSON 为 `api.use_system_proxy: false`；工作区会保存该选择，继续批次后可核对开关。

`HTTP 未确认` 表示没有收到可确认的 HTTP 响应，不等于整批执行时间超过上限。连接可能在配置时限前被代理、TLS 或网络断开。异常会记录脱敏的错误类型、连接模式及尝试次数；不输出底层异常中的代理地址、凭据或响应正文。可对同一个只读接口比较系统代理与直连耗时，再选择适合该服务器的连接方式。

### HTTP 504 与耗时较长的刷新

`refresh_song_file_cache` 是同步操作，会重新遍历歌曲目录，并在服务端开启哈希预计算时重算文件哈希；它不只处理本批新曲目。库较大时，反向代理可能在后端完成前返回 504。此时 `code=None` 表示没有收到可解析的管理 API 结果，不能据此断定后端没有执行。

Uploader 对普通请求等待 120 秒，对系统操作 POST 等待 360 秒，并在异常中记录耗时。但客户端增加等待时间无法阻止 Nginx 提前超时。可在该站点已有的代理 `location` 中增加 `proxy_read_timeout 300s;`，保留原有上游和请求头配置，备份后通过 `nginx -t` 再平滑重载。若实际操作耗时更长，需要协调两端上限，或由服务端提供异步任务与状态查询。

遇到 504，当前步骤记录为“结果未确认”，后续购买项、定数及刷新不会继续。应先查看代理与应用日志，确认后端已经结束，再从原工作区继续 03；无需重新执行 01/02。成功步骤跳过，结果未确认的刷新会重新执行，不会凭日志中的 HTTP 200 自动标记成功，也不在请求失败后自动重发。

对已经完成的手动上传任务再次明确执行，会建立新的上传确认并重新刷新资源，避免 songlist 没变但 bundle/媒体已更新时沿用旧缓存。业务数据仍按检查点补缺，不重复新建；未完成任务的重试则继续原确认和进度。

原始批次仍有 ERROR 时不能只对成功子集执行 03。历史预处理报告也必须先通过“继续预处理”重新核验；已保存的独立 03 任务则可以脱离原资源工作区载入。
