# 03 服务端操作与最终提交

03 从 02 的文件上传阶段独立出来。流程为 **01 准备审核 → 保存总表 → 02 打包上传 → 03 操作 → 确认提交**。API 操作可按选项跳过，工作区要到最终确认提交后才销毁。

01 已在工作区内保存定数草稿和本批购买候选。02 上传核验后交接到同一工作区的 `server-task.json`，保留所有资源和进度；也支持已手动上传的独立任务。预处理、检查和定数录入不会自行修改 VPS。

## 界面与定数录入

1. 预处理或检查本批曲目，下方“03 · 定数与服务端”显示这批 SID、English name 和难度 0–4。
2. 双击实际谱面的定数单元格，输入后按 Enter 或点击“保存定数”。只保存用户填写的数据，不从 rating 推断。整数按 `.0` 显示，也可填一位小数；服务端将 0 视作未知，故已知定数填写正数，未知留空。
3. 点击“审核总表…”选择人工保存、且确实用于本次上传的最终 songlist。03 只提取本批 ID，重新读取最终 `set`、`purchase` 和曲名，不继续使用原始单曲包中未审核的字段。`title_localized.en` 优先，缺少时取 `title`。
4. “选项…”可逐项跳过操作。“执行 03…”确认目标 API、上传情况及未填定数；全部关闭时明确记录跳过，不连接 API。成功后验收结果，点击“提交并清理…”完成整批工作区。

真实谱面难度以本次资源检查中的输入与本地服务端实际 AFF 并集为准，排除 timing-only 占位谱；不会把已存在的真实旧难度误记为空。没有实际谱面的单元格固定 `-1`，不能编辑。

存在未填真实难度时弹窗，用户可返回补填，也可继续：**保留远端已有定数；新建记录的未填项暂用 -1**。空难度统一 `-1`。已有歌曲使用局部 PUT，未填写的真实难度不会覆盖已有值。SID 与曲名取自审核总表，增量添加难度也可以补录。

## 执行顺序

| 顺序 | 操作 | 实际入口 |
| --- | --- | --- |
| 1 | 刷新 bundle、songs、world map | `refresh_content_bundle_cache` → `refresh_song_file_cache` → `refresh_world_map_cache` |
| 2 | 补充缺少的购买项 | `/items` → `/purchases` → `/purchases/<name>/items` |
| 3 | 新增 / 补充歌曲定数 | `POST /songs` 或 `PUT /songs/<sid>` |
| 4 | 刷新曲目定数对应的成绩评分 | `refresh_all_score_rating` |

第 4 项对应旧 Web 页 `/updatedatabase/refreshsongrating`，会重新计算 best_score、recent30 中已有成绩的评分；没有额外调用“刷新用户 PTT”操作。各项开始前先做只读鉴权和结构检查，所有写操作仍严格按上表顺序。

## 购买项规则

- 空 purchase 不创建购买项；`purchase == id` 为 `single`、价格 100；`purchase == set` 为 `pack`、价格 500。
- 同一个曲包被多首歌引用，只处理一次。purchase 不匹配两者、两者同时匹配或同名出现不同类别时报告 ERROR，不猜测物品类别。
- 先查询远端。已存在的购买项保留价格、折扣和物品配置，不修改已有业务数据。
- 新建时 `price == orig_price`，折扣起止使用 2000 年的过去时间，`discount_reason` 为空，不启用兑换券购买。
- 新物品设为可用；已有但不可用的物品需要人工确认。先创建物品，再创建购买信息，最后关联一个同 ID 的 `single` / `pack`、数量 1。

API 请求后读回核验。若本任务创建购买项后中断，会记住创建意图，下次先读取服务端状态，再补未完成关联；不会因为“购买项已经存在”就误跳过半成品，也不会重设其他既有购买项。

## 保存、清理与重试

01 之后的任务和草稿位于工作区内，纯预检保持只读：

```text
<release_root>/<batch-id>/server-task.json
```

记录本批曲目、真实难度、人工定数、购买候选、审核哈希、选项与进度；资源文件同处工作区，不保存 Token 或密钥内容。购买候选依据最终 set / purchase 生成，03 查询远端后只补缺少项。通过工作区管理恢复可同时还原 server 配置。

02 使用 `confirm_uploaded(task, receipt)` 绑定上传凭据与最终总表；此时不清理。03 完成后记录当前曲目、定数、选项、上传确认及 API 目标的完成指纹；修改输入后不能凭旧完成状态提交。最后确认提交才清理临时资源，在 `.history` 留摘要、`.server-tasks` 留完成任务归档。独立手动上传任务也使用 `.server-tasks`，由用户确认上传情况。

每个 API 步骤保存检查点。任何失败停止后续步骤，不回退已成功的数据；后续使用同一任务继续。API 请求不自动重试，超时或响应丢失可能意味着服务端已处理：购买项与歌曲先查询再补缺，刷新请求结果不明时需确认服务端处理结束再继续。任务有跨进程锁和修订号，避免两个窗口同时执行或旧窗口覆盖新进度。若确认后的审核表又改变，必须重新载入并确认上传情况。

对已经完成的手动上传任务再次明确执行，会建立新的上传确认并重新刷新资源，避免 songlist 没变但 bundle/媒体已更新时沿用旧缓存。业务数据仍按检查点补缺，不重复新建；未完成任务的重试则继续原确认和进度。

原始批次仍有 ERROR 时不能只对成功子集执行 03。历史预处理报告也必须先通过“继续预处理”重新核验；已保存的独立 03 任务则可以脱离原资源工作区载入。
