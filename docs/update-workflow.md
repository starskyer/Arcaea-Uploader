# 三阶段更新流程

采用「01 准备审核 → 02 打包上传 → 可选 03 服务端操作」。当前已实现预处理、工作区管理、预检和 03 编辑/执行；完整 01/02 资源准备与上传仍待接入，按钮保持禁用。03 也可对已手动上传的批次独立执行。

日常操作目标：选择目录和 version → 01 → 人工审核保存 → 02 → 可选 03。预处理和检查是辅助入口，01 内部自动执行；不要求用户搬运标准副本。03 可以单独跳过或稍后继续。

## 第一步：prepare

1. 扫描输入根目录全部曲目，内部自动预处理并检查资源，整理嵌套结构、别名、图片、音频与空谱，校验来源、ID 和已有资产，建立本次发布清单。必须检查本次实际输入，不能依赖此前辅助操作的过期结果。
2. 以本地现有资源为基线，在发布工作区合入曲绘、背景及完整下载资源，补缺失的 `0–2.aff`；保留原始曲目包。
3. 合并总 songlist，生成字段冲突报告。普通字段已有值与输入不同则保留旧值，报告 WARNING 交给人工审核；新增字段、难度可自动合入。本批 version 强制使用界面指定值，remote_dl=true，无实际谱面的已声明难度 rating=0；按现有总表初始化的对应表补充缺失翻转背景。背景尺寸未知属于 ERROR，必须解决后才能发布。
4. 基于合并草案完成图片和预览准备，保留生成预览所需的完整源音频以及输入快照。
5. 输出本次待审核总 songlist、冲突报告、资源状态。Windows 默认用记事本打开**该发布工作区的总 songlist**，然后结束第一步，等待用户编辑保存。

准备好的下载资源在本地发布工作区保存 `database/songs/<id>/` 的最终结构；第一步不触发 VPS 上传、不运行 Bundler、不推进 `metadata.oldjson`。工作区隔离保证多次人工编辑不会意外影响正在运行的服务端。审核并发布时再安装到实际本地 database，保持「本地先完整、VPS 后同步」的顺序。

若存在 songlist 字段冲突，仍生成可编辑草案并报告 WARNING；资源本身无法准备的错误单独标为 ERROR。当前 `plan` 仅有 WARNING 时可通过预检，但仍须人工审核；任一 ERROR 则令批次无效。

## 人工审核交接

用户人工检查并保存总 songlist，再明确执行第二步。记事本窗口关闭不应自动触发发布，文件修改时间也不等于审核确认。即使无需改动，执行第二步也表达了已审核。

发布工作区应绑定本次输入、资源基线、自动合并草案和版本历史的哈希，避免审核期间输入变更或另一次发布覆盖状态。第二步使用已保存的总表，不再次自动合并并覆盖人工编辑。服务端下载资源涉及人工新增引用时，必须核验相应文件存在。

## 第二步：publish

1. 读取明确指定发布工作区中的已保存 songlist，检查 JSON、ID、idx、难度、资源引用及第一步的阻断项。检测审核期间输入或基线漂移。
2. 比较预览字段；若人工改了起止时间或相关音频配置，从保留的完整源音频重建对应预览，不能因为 `preview.ogg` 已存在就跳过。
3. 校验全部准备产物，将审核后的工作结果应用到完整 assets 基线，保存打包前历史，调用 Bundler。输出到工作区，不放入输入 assets；默认沿用历史应用版本并按递增后的 `versionNumber` 命名。取消“沿用当前应用版本”并填写新版本时，将新版本同时用作 JSON 的应用版本与 bundle 版本，文件名前缀为 `<新应用版本>.0`，作为承接包保留上一版本链。
4. 验证 `.cb` 与 `.json`、版本链、数据范围及哈希，并检查增量历史确实按预期写入。外部工具的零退出码不足以证明成功。
5. 将同一批下载资源和 bundle 安装到本地服务端 database，核验通过后，再通过 SSH 上传 VPS。保留本地发布快照和清单供重试。
6. VPS 暂存、校验、就位，最后发布 bundle JSON。保存绑定最终审核 songlist 哈希和真实谱面清单的独立 03 任务，记录 02 完成后清理临时大文件。02 不再调用资源刷新或业务 API。

程序分别记录构建、本地完成、上传完成与 03 状态；失败时继续相应阶段。

## 可选第三步：服务端操作

重新读取人工保存并用于上传的最终 songlist，只处理本批 ID。按顺序刷新 bundle、songs、world map；仅补不存在的购买项；写入人工指定定数；最后调用 Web“刷新曲目定数”对应的 refresh_all_score_rating。

purchase 等于 id 为单曲 100，等于 set 为曲包 500，price 与 orig_price 相同，折扣时间已过期、不允许兑换券。已有购买项保留，新增项按物品、购买信息、物品关联处理；类别冲突报告 ERROR。

定数在下方按 SID、英文曲名、难度 0–4 录入，不从 rating 推断，空难度固定 -1。真实谱面未填时弹窗；允许继续并保留已有值，新建记录未填暂用 -1。各项可跳过，详见[03 服务端操作](server-operations.md)。

## 状态与恢复

| 状态 | 说明 | 继续方式 |
| --- | --- | --- |
| 待人工审核 | 第一阶段已完成或已产生可审核草案 | 编辑保存，然后执行第二步 |
| 资源待处理 | 未知背景尺寸、缺文件或文件冲突等 | 修复资源后重新准备，不发布 |
| 构建失败 | 尚未验证 bundle 完整性 | 核验/恢复本次历史快照，再重试构建 |
| 本地完成 | 本地 database 已校验 | 继续 VPS 传输 |
| 上传完成、03 待处理 | 02 已成功，尚未执行可选操作 | 载入独立 03 任务执行或继续跳过 |
| 03 失败或结果不明 | API 进度已记录 | 核对后只补未完成步骤 |
| 服务端确认未运行 | 文件就位，等待服务启动加载 | 记录待加载，不自动启动进程 |

Bundler 会写回 `metadata.oldjson`。上传失败时复用已生成的发布文件，不重新递增版本。构建失败后只能在确认没有后续构建、没有安装/发布该版本时恢复历史。禁止同一资源基线并发构建。历史 bundle 及远端独有文件不执行镜像删除。

多文件就位不是天然事务；JSON 最后发布只能降低不完整 bundle 被索引的风险。实现时还要处理覆盖备份、失败回退、运行中下载和多进程缓存一致性。

上传失败时保留临时工作区。完整 02 接入后，本地、远端文件核验成功并保存独立 03 任务（或明确跳过）即可清理大文件。03 失败只保留小任务和检查点，无需恢复大文件；不能因为预处理完成就清理。详见[工作区管理](workspaces.md)。

## SSH 和 API

VPS 配置主机 IP、端口（默认 22）、用户名、密钥和服务端项目根目录。`latest version/database` 作为可配置相对路径，正确处理空格和 Windows 本地路径。仅传输发布清单内容，不同步用户数据库与日志。

API 地址和具有 `system` 权限的 Token 单独配置。刷新使用 `Token` 请求头与 `{}` JSON 请求体，检查 HTTP 状态及 `code == 0`。401/403 是鉴权问题，404 或超时不能直接判断成未运行。SSH 可连接也不代表服务端已启动；未确认状态时保留待处理状态。
